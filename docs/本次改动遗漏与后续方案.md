## 二、功能性遗漏（建议优先处理）

### 2.1 FCM 使用已停用的 Legacy API（高优先级，当前生产不可用）

**问题**：`notify_service.py:_send_fcm()` 调用
`https://fcm.googleapis.com/fcm/send` + `Authorization: key=<server_key>`。
该 **Legacy HTTP API 已于 2024-06 被 Google 关停**，现有调用会返回 404，FCM 推送实际不工作。

**方案**：迁移到 **FCM HTTP v1 API**。
- 配置改为 Service Account JSON（`GOOGLE_APPLICATION_CREDENTIALS` 或内嵌密钥），不再用 server key。
- 用 `google-auth` 获取 OAuth2 access token，POST 到
  `https://fcm.googleapis.com/v1/projects/<project_id>/messages:send`，body 用 `{"message": {"token": ..., "notification": {...}, "data": {...}}}`。
- 逐 token 发送；失效 token（`UNREGISTERED`/`INVALID_ARGUMENT`）应从 `UserPushToken` 清理。
- 新增配置：`FCM_PROJECT_ID`、`FCM_CREDENTIALS_JSON`（替换 `NOTIFY_FCM_SERVER_KEY`）。
- 依赖：`firebase-admin` 或 `google-auth` + `httpx`。

**估算**：0.5 天。

### 2.2 富途 / 老虎组合（多腿）止损止盈未覆盖

**问题**：仅 IBKR 实现了多腿 combo 保护单。
- `futu/adapter.py:place_protective_orders()` 用 `signal.symbol` 构造单 `code`，**多腿信号会失效或只保护第一腿**。
- 老虎（cloud-executor）侧未见组合保护单逻辑。

**方案**：
- 富途无原生 combo，按腿拆单提交反向保护单（参考已有 `_place_combo_order` 拆腿逻辑），或在多腿场景显式返回 `{"status":"unsupported"}` 并落审计，避免“静默部分保护”。
- 老虎确认是否支持组合腿；不支持则同样显式标记 unsupported。
- 统一约定：多腿保护单要么全成功要么全回滚（避免裸保护腿）。

**估算**：富途 0.5 天 / 老虎 0.5 天。

### 2.3 Agent 自动更新的落地缺口

**问题**（`updater.py`）：
1. **无完整性校验**：下载包未校验 checksum/签名，存在被篡改下载风险。
2. **非 frozen（开发）模式**：`apply_update` 只保存文件不替换，符合预期但无提示用户。
3. **macOS `.dmg`**：仅 `open` 弹出，需手动拖拽安装，非真正自动更新。
4. **替换后未重启**：PyInstaller onefile 替换二进制后仍运行旧进程，需用户手动重启才生效。

**方案**：
- version-check 响应增加 `sha256` 字段，下载后校验再 apply。
- Windows/Linux onefile：替换后用 `os.execv` 或生成 `.bat`/脚本延迟替换并重启。
- macOS：改为分发 `.zip`（内含 .app）走解压替换路径，而非 `.dmg`；或集成 Sparkle。
- 替换成功后给出“需重启”通知（托盘）或自动重启。

**估算**：1 天（跨平台测试占大头）。

## 三、配置 / 部署遗漏（中优先级）

### 3.1 GeoIP 路径双约定

- `config.py` 默认 `data/geoip/...`（相对路径，非 Docker 本地用）。
- docker-compose / `.env.example` 用 `/app/data/geoip/...`（容器内）。
- 另有 `services/api-server/data/geoip/README.md` 指向本地路径。

**风险**：本地非 Docker 跑 api-server 时若不设置环境变量，会找相对路径、易困惑。
**方案**：在 `services/api-server/data/geoip/README.md` 与根 readme 中明确“本地 vs Docker 两套路径”，或统一在 config 注释说明。

### 3.2 入站 Webhook 无本地 dev 验签旁路

**问题**：`RESEND_WEBHOOK_SECRET` 未配置时 `/mail/webhook/received` 直接 401，本地无法 mock 测试。
**方案**：增加 `ALLOW_INSECURE_INBOUND_WEBHOOK=true`（仅 dev）跳过 Svix 验签，或提供一个带签名的本地测试脚本。

### 3.3 入站回复的发件域可能未验证

**问题**：`reply_inbound_mail` 用收件地址 `to_addresses[0]` 作为回复 `from`，若该域未在 Resend 验证，发信会被拒。
**方案**：回复发件人固定用已验证的 `RESEND_FROM_EMAIL`，原收件地址放 `Reply-To`/正文，或在 admin UI 显式选择已验证发件人。

### 3.4 CORS / 生产域名

**问题**：`CORS_ORIGINS` 默认仅 localhost，docker-compose 未透传，生产部署前端域名需手动加。
**方案**：在 `.env.example` 与 compose 暴露 `CORS_ORIGINS`，readme 标注生产必改。

### 3.5 Telegram Webhook 需手动 setWebhook

**问题**：ingest 提供了 webhook 端点，但未见自动 `setWebhook` 注册，需运维手动调用 Telegram API。
**方案**：补一个启动注册脚本或 readme 操作说明（含 `TELEGRAM_WEBHOOK_SECRET` 用法）。

## 四、数据库迁移（中优先级）

**现状**：新表 `user_geo_events` / `inbound_emails` / `user_push_tokens` 依赖启动 `Base.metadata.create_all`（对已有库会建缺失表，OK）；列变更靠 `seed._apply_light_migrations` 手写 `ALTER TABLE ... IF NOT EXISTS`。

**遗漏**：
- 无正式 Alembic 迁移版本，schema 演进不可回滚、无版本追踪。
- `_apply_light_migrations` 不含新表的索引/约束补丁（新表由 create_all 带，存量库若曾手工建表可能缺索引）。

**方案**：
- 引入 Alembic baseline（autogenerate 当前模型），后续变更走 migration。
- 过渡期保留 `_apply_light_migrations` 作兜底，新功能新增列同步补一条 ALTER。

**估算**：0.5 天（baseline）。
