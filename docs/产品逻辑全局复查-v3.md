# 产品逻辑全局复查 v3（端到端业务视角）

> 视角：不只看代码 bug，而是从**信号生命周期、风控、计费、多租户、安全**的产品完整性出发。
> 本文整理发现的逻辑遗漏与改动方案，**未改代码**。
> 关联：代码级问题见 `全局代码复查与改动方案-v2.md`（已修复）；本文是更上层的产品逻辑层。

---

## 一、信号链路完整性（最影响产品可信度）

端到端链路：`ingest → 解析 → signal-router → resolve-routing(风控/额度) → cloud-executor / relay-gateway → agent → 执行回报`

### 🔴 P0-1 幂等闭环未关闭：成功成交后仍可能重复下单
- **现象**：`signal-router` 成功路径只写 `ExecutionRecord(status=ROUTING)`（`router.py:98`）；真正成交回报走 `/execution-report`（`internal.py:111-143`），但它**既不更新 ExecutionRecord，也不写幂等缓存**。幂等缓存只在 `/execution-record` 收到终态时设置（`internal.py:167-169`），而 `cloud_executed` 字符串其实从未作为 record 落库。
- **后果**：TradingView/webhook 重复推送（很常见）在一笔已成交后，幂等查不到终态 → **二次下单**。
- **方案**：
  1. `/execution-report` 收到终态（`FILLED/PARTIALLY_FILLED/REJECTED/CANCELLED/FAILED`）时 upsert 对应 `ExecutionRecord` 状态，并 `idem_cache_set`。
  2. `check-idempotency` 同时查 `execution_reports`。
  3. 幂等键补 `user_id` 维度（`internal.py:275-286` 目前 `(source_id, signal_id, account_id)` 无租户隔离，跨租户同名信号会碰撞）。

### 🔴 P0-2 执行记录永远停在 ROUTING，用户看不到结果
- **现象**：`ExecutionRecord` 创建后无任何路径用回报更新它；`execution_reports` 表**没有任何用户可见 API**（仅 `internal.py` 写入）。Dashboard `/config/executions` 只显示 `status·broker·signal_id`，于是用户永远看到「ROUTING」，看不到成交价/订单号/失败原因。
- **方案**：
  - 用回报更新 record 的 `status/detail`（与 P0-1 同一处改造）。
  - 新增 `/config/executions` 合并最新回报，或单独暴露 `execution_reports`（按 `(signal_id, account_id)` 取最新）。

### 🟠 P1-3 多处「静默丢信号」无审计无通知
- **现象**：
  - `resolve-routing` 失败 → `router.py:62-64` 返回空 plans，但 ingest 仍回 `accepted` → 信号凭空消失。
  - 额度/kill_switch 拦截时 `routing.py:111` 丢弃 `_reason`，无 `risk_blocked` 也无通知；`router.py:78-83` 空 bindings 直接 `continue`。
- **方案**：拦截/失败要落 `ExecutionRecord(status=SKIPPED/BLOCKED, detail=reason)` 并 `notify`，让用户知道「为什么没下单」。

### 🟠 P1-4 幂等检查 fail-open
- **现象**：`router.py:40-42` 异常时返回 `False`（放行）。Redis/api-server 抖动 → 重复执行。
- **方案**：交易类动作建议 fail-closed（异常时跳过执行并通知），或至少保证 DB 兜底查询可用。

### 🟡 P2-5 部分成交语义不一致
- `PARTIALLY_FILLED` 在 `core.py:151-153` 当最终成功处理，但在 `order_status.py` 是非终态，且不在通知/幂等终态列表里 → 用户收不到部分成交通知、可能重复执行。

### 🟡 P2-6 Agent 离线即丢弃，无队列/重放
- relay-gateway 离线直接 `delivered:false`（`main.py:191-192`），无离线队列、无重连重放。Agent 短暂掉线期间的信号全部丢失（已记录 `DISCARDED_AGENT_OFFLINE` 并通知，但不可恢复）。
- **方案**：可选的离线信号 outbox + 重连重放（需考虑过期信号不应补单的风控）。

## 二、风控（资金安全）

### 🔴 P0-7 `max_daily_loss_usd` 实际未生效
- **现象**：`risk_service.py:39-56` 从 `ExecutionRecord` 里按 `FAILED/REJECTED/DISCARDED` 状态、用 `signal.limit_price` 估算"损失"。但真实盈亏在 `execution_reports`，且 FAILED 订单根本没有成交亏损。等于**日亏损限制形同虚设**。
- **方案**：从 `execution_reports` 的成交回报聚合真实已实现盈亏；或对接券商持仓/盈亏接口。

### 🟠 P1-8 止损止盈下单失败无感知
- `core.py:249-250` 保护单失败只记日志，用户已有持仓却无 SL/TP，且不知情。
- **方案**：保护单失败要发 `/execution-report`（status 含 protective_failed）+ 通知用户。

### 🟠 P1-9 富途多腿仍是「逐腿保护」，老虎/IBKR 语义需实盘验证
- v2 已修数量与回滚，但富途无原生 combo，多腿组合的保护仍是各腿独立单，价差组合的真实风险敞口与单腿保护不等价。
- **方案**：文档明确「富途多腿为尽力保护」；关键策略建议用 IBKR combo；老虎 combo 平仓方向需实盘验证。

### 🟡 P2-10 `execution_config`（重试/超时/轮询）永远为 None
- `routing.py:134` 没有把每用户执行参数传给 executor，ExecutionCore 只能用默认值。属未接线的预留能力。

## 三、会员计费与额度（变现与公平性）

### 🔴 P0-11 计划额度大面积未在服务端强制
- `max_signal_sources` / `max_brokers` / `ai_parse` / `multi_agent` 仅在前端 `FeatureGate` 或计划展示中体现，**创建端点不校验**：
  - 信号源创建 `config.py:203-287`、`users.py:96-116`
  - 券商绑定/凭证 `users.py:136-168`
  - AI 解析 `internal.py:238-256`（free 也能用 OpenAI，产生成本）
  - Agent token `users.py:84-93`（multi_agent 无限制）
- **后果**：付费墙可被绕过；AI 成本失控。
- **方案**：在各创建端点调用 `has_feature` / 计数校验，超限返回 402/403。

### 🟠 P1-12 Stripe 取消/欠费即时降级，无账期宽限
- `subscription.deleted` 立即降级到 free（`stripe_webhook.py:106-119`）；`past_due` 被 `get_active_plan` 排除（`entitlements.py:23`）→ 一次扣款失败立即失去权益。
- **方案**：取消后保留权益到 `period_end`；`past_due` 给宽限期。

### 🟠 P1-13 未知 Stripe price 回退到 pro
- `stripe_webhook.py:77-79` 找不到 price 时默认按 pro 开通 → 配置错误会白送 pro。
- **方案**：未知 price 记录告警并维持原计划，不默认升级。

### 🟡 P2-14 额度默认值不一致
- `entitlements.py:40` 默认 `max_daily_trades=10`，seed free 计划是 5（`seed.py:65`）。无计划用户与 free 用户行为不同。

## 四、安全与多租户（上线前必处理）

### 🔴 P0-15 默认密钥 + 无签名校验旁路
- `JWT_SECRET=dev-jwt-secret-change-in-prod`、`INTERNAL_SECRET=dev-internal-secret`、`ADMIN_TOKEN=dev-admin-token-change-me`（`config.py:10-11`、`admin.py:20`）默认值可用。
- `STRIPE_WEBHOOK_SECRET` 未设时跳过签名校验（`stripe_webhook.py:25-28`）。
- **方案**：生产启动时若仍为默认值/空则**拒绝启动**（fail-fast 校验）。

### 🔴 P0-16 认证端点无任何限流
- login/register/forgot/reset/refresh/google 全无 rate limit（全仓库无限流）→ 撞库/枚举/邮件轰炸。
- **方案**：接入 IP+账号维度限流（slowapi / Redis 计数）。

### 🟠 P1-17 Refresh token 无轮换/吊销，登录不校验 is_active
- `auth.py:51-60` refresh 不校验用户存在/启用，不轮换；邮箱登录不查 `is_active`（Google 登录查了）。
- **方案**：refresh 校验用户状态 + 轮换；统一 `is_active` 校验；考虑 token 版本号/黑名单。

### 🟠 P1-18 Discord OAuth 回调未鉴权且 state=明文 user.id
- `config.py:97,115-136` 回调无鉴权、`state` 为裸 `user.id`，攻击者可给受害者的 Discord 源塞 `guild_id`。
- **方案**：签名 state（HMAC + 过期）或要求登录态。

### 🟠 P1-19 邮箱验证强制不彻底
- `REQUIRE_EMAIL_VERIFICATION=true` 时仍有：注册/登录即发 JWT、存券商凭证、Stripe checkout、AI 预览（`users.py:139/156`、`subscriptions.py:32/54`、`config.py:370`）不走 `get_verified_user`。
- **方案**：把交易凭证、计费、AI 预览纳入 `get_verified_user`。

### 🟡 P2-20 凭证 config 明文 + cloud-executor 接受内联凭证
- `BrokerCredential.config`（tiger_id/account/license/env）明文存（`users.py:164`）；cloud-executor 接受 payload 内联 `broker_credentials` 明文路径（`executor.py:28-29`）。
- **方案**：敏感 config 字段一并加密；移除/限制生产内联凭证路径；FERNET 支持轮换。

### 🟡 P2-21 内部端点信任调用方传入的 user_id
- `execution-record/notify/agent-presence/parse-signal` 等用调用方传的 `user_id`，仅靠 `INTERNAL_SECRET` 信任边界。一旦 secret 泄漏可越权。
- **方案**：保持内网隔离 + 轮换 secret；关键写操作可加二次校验。

## 八、建议落地批次（原始规划，供追溯）

1. **资金安全批**（P0-1/2/7、P1-8）：幂等闭环 + 执行记录回写 + 日亏损改聚合回报 + 保护单失败通知。这是「自动跟单」最核心的可信度。
2. **变现与防滥用批**（P0-11、P1-12/13）：服务端额度强制 + Stripe 生命周期修正。
3. **上线安全批**（P0-15/16、P1-17/18/19）：密钥 fail-fast + 限流 + refresh/OAuth/邮箱验证加固。
4. **体验与运维批**（P1-3、P2 系列）：失败可见性、离线重放、correlation_id、指标。
