# 产品逻辑复查 v4：本轮改动自查 + 剩余问题方案

> 背景：v3 已落地资金安全/变现/上线安全四批修复。本文做两件事：
> 1. **自查 v3 改动是否引入新问题**（最该先看）；
> 2. 继续往下挖**剩余/新发现问题**，给出方案。**本文未改代码**。

---

## A. 本轮改动的自查发现（建议优先处理）

### 🟠 A1. 幂等 fail-closed 的副作用：api-server 抖动时信号被静默跳过
- **位置**：`signal-router/app/router.py` `_is_duplicate` 异常时返回 `True`（按重复跳过）。
- **问题**：为防重复下单改成 fail-closed 是对的，但现在「真重复（缓存命中）」和「检查失败（api-server 抖动）」都返回 `True`，且 `_route_one` 直接返回 `duplicate` outcome——**不落记录、不通知**。api-server 短暂不可用时，整批信号会无声消失。
- **方案**：让 `_is_duplicate` 区分三态（重复 / 不重复 / 检查失败）。检查失败时：仍跳过执行，但落 `DEFERRED` 记录 + 通知用户「因系统繁忙暂未执行」，或做 1~2 次短重试后再决定。

### 🔴 A2. 「在飞窗口」竞态：dispatch 与回报之间仍可能重复执行
- **位置**：`_route_one` 先写 `ROUTING`（非终态）再 dispatch；`check-idempotency` 只认终态。cloud-executor / agent 本地无统一幂等。
- **问题**：成交回报到达前（几百 ms~数秒），若同一 `signal_id` 重复推送，幂等查不到终态 → **二次下单**。这是 v3 闭环没覆盖的窗口。
- **方案**（二选一）：
  1. **在飞去重**：`check-idempotency` 把 `ROUTING/DISPATCHED` 记录在「最近 N 秒」内也视为重复（占位锁），回报回写终态后正常。
  2. cloud-executor 执行前自己调 `check-idempotency`（双重保险）。
- 推荐方案 1（改动集中在 api-server，且对 relay/cloud 都生效）。

### 🟠 A3. cloud-executor 执行期不检查 kill_switch
- **位置**：`cloud-executor/app/executor.py` 创建 `ExecutionCore` 时未注入 `should_continue`。
- **问题**：用户在 resolve-routing 之后、cloud 真正下单之前开启急停，老虎单仍会下出去（relay 路径有 `should_continue` 兜底，cloud 没有）。
- **方案**：执行前查一次 `user.kill_switch`（或让 cloud-executor 注入 `should_continue` 回调，下单前回查 api-server）。

### 🟡 A4. `protective_failed` 用的是通用 execution 模板，文案不够明确
- **位置**：`internal.py` execution_report 对 `protective_failed` 触发 `kind="execution"` 通知。
- **方案**：加专门模板「保护单下单失败，持仓暂无止损/止盈，请手动检查」，提升告警可读性。

## C. 本轮新发现的较小问题

| 编号 | 问题 | 位置 | 方案 |
|------|------|------|------|
| C1 | refresh 只「校验 is_active + 重发」，**未真正吊销旧 refresh token** | `auth.py` refresh | User 加 `token_version`，签发时带上、decode 时比对；登出/改密时自增即吊销全部旧 token |
| C2 | 密码策略仅 `min_length=8` | `schemas.py` | 增加复杂度校验（大小写/数字/长度≥10）或接入 zxcvbn 强度 |
| C3 | `plan_features` 默认 `max_daily_trades=10` 与 seed free=5 不一致 | `entitlements.py:40` | 默认值对齐 seed free（=5），避免无 plan 用户与 free 行为不同 |
| C4 | 多个 active membership 时按 `period_end` 排序，NULL 并列不确定 | `entitlements.py` | 增加 `created_at` 次级排序，取最新 |
| C5 | webhook HMAC 未配置即放行 | `ingest/connectors/webhook.py` | 生产（APP_ENV=production）强制要求 hmac_secret，否则拒绝该源 |
| C6 | 注册即返回 JWT（即便要求邮箱验证） | `auth.py` register | 可选：要求验证时注册不返回 access token，仅返回「待验证」状态 |

---

## D. 建议执行顺序

1. **A2 在飞去重**（堵住最后一个重复下单窗口）+ **A3 cloud kill_switch**（资金安全收尾）。
2. **A1 fail-closed 可见性** + **A4 保护单告警**（避免静默 + 告警清晰）。
3. **C1 refresh 吊销** + **C5 生产 HMAC 强制**（安全收尾）。
4. **C3/C4** 顺手修（低风险小改）。
5. B 系列（P2 增强）按需排期，不阻塞上线。

---

## 结论
v3 的四批修复整体是对的，但留下两个**资金安全收尾项**（A2 在飞竞态、A3 cloud 急停）值得紧接着补上；A1 是我引入 fail-closed 的副作用，需要补可见性。其余多为增强项。
