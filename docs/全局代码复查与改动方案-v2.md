# 全局代码复查与改动方案 v2（P0–P3 实现后）

> 复查时间：实现 FCM v1 / 富途老虎 combo / Agent 更新 / Alembic / 收件箱等之后。
> 本文记录复查发现的新问题与改动方案，**不直接改代码**，供决策后再实施。

## 总览

上一轮 P0–P3 功能均已落地且单测/构建通过，但复查发现 **3 个高 + 12 个中 + 10+ 低** 问题，主要集中在：
1. **异步路径里的同步阻塞 I/O**（FCM token 刷新、send_email、附件下载）——影响 api-server 吞吐与稳定性。
2. **多腿期权保护单的数量/价格语义**——存在下错单量、保护腿不全的实盘风险。
3. **若干启动顺序 / 一致性 / 文案细节**。

---

## P0（高）— 必须修

### H1. FCM token 刷新阻塞事件循环
- **位置**：`services/api-server/app/services/fcm_service.py:48`（`creds.refresh(Request())`），由 `send_fcm_to_tokens()`(async) 在第 70 行同步调用。
- **问题**：`google.auth.transport.requests.Request` 走同步 `requests` 库，会阻塞 asyncio 事件循环；每次 `deliver()` 通知都触发，高并发下拖垮 api-server。
- **方案**：
  - 把 `_access_token()` 的 `refresh` 放进 `await asyncio.to_thread(creds.refresh, Request())`；或改用 `google.auth.transport.aiohttp`/手动用 httpx 走 OAuth2 token endpoint。
  - 缓存 access token（Credentials 自带 `expiry`，仅在过期前 60s 才 refresh），避免每条通知都刷新。

### H2. FCM 刷新失败会 500 整个通知事务
- **位置**：`fcm_service.py:42-49`（`_access_token` 无 try/except）。
- **问题**：凭证错误或网络异常会向上抛，使 `deliver()` → `/internal/notify` 500，连带回滚站内通知/邮件写库。
- **方案**：`_access_token()` 包 try/except，失败返回 `None` 并 `logger.warning`，FCM 静默降级，不影响其余通知渠道。

### H3. 富途多腿保护单对每条腿都用 combo 总量
- **位置**：`packages/core/sigtrades_core/brokers/futu/adapter.py:536-545`（`_place_leg_protective` 用外层 `qty = signal.quantity or 1`）。
- **问题**：`OptionLeg.quantity`（models.py:73）/ratio 被忽略，多腿组合各腿数量按总量下单，导致保护单数量错误（实盘风险）。
- **方案**：`_place_leg_protective` 接收 per-leg 数量参数，多腿分支传 `leg.quantity or qty`；与 `_place_combo_order` 的拆腿数量逻辑保持一致。

## P1（中）— 应修

### M1. 异步处理器内的同步阻塞（通用）
- **位置**：
  - `notify_service.py:77` `send_email()`（同步）在 `async deliver()` 内调用。
  - `admin.py:383` `fetch_inbound_attachment()`（内部 `httpx.get` 同步）在 `async download_inbound_attachment` 内。
  - `inbound_mail_service.py:221,228` 同步 `httpx.get`。
- **方案**：统一用 `await asyncio.to_thread(...)` 包裹，或把这些函数改为 async + `httpx.AsyncClient`；`send_email` 可做成 async 包装。

### M2. 富途/老虎多腿保护单价格按净价均摊
- **位置**：`futu/adapter.py:559`（`per_leg_fill = fill_price / len(legs)`）；`tiger/adapter.py:744-755`（combo 级 `fill_price` + signal 级方向）。
- **问题**：价差组合各腿权利金不同，均摊估算会让止损/止盈价偏离实际，触发价不准。
- **方案**：
  - 优先用各腿实际成交价（若 `place_order` 回执含 per-leg fill 则透传给保护单）。
  - 富途无原生 combo，明确按腿保护；老虎尽量用 combo 净价单（单一组合 STP/LMT），与 `place_order` 的 `action='BUY'` combo 语义对齐。

### M3. 多腿保护单的"部分保护"风险
- **位置**：`futu/adapter.py:557-569`（逐腿下单，无回滚）。
- **问题**：部分腿下单成功、部分失败时，留下裸保护腿，无补偿/回滚。
- **方案**：要么全成功要么回滚已下保护单（参考 `_place_combo_order` 的失败撤单逻辑）；或失败时返回 `partial` 状态并落审计 + 通知用户。

### M4. 老虎保护单缺少连接检查 & combo 方向不一致
- **位置**：`tiger/adapter.py:705-759`（无 `self.connected` 检查；`combo_order(action=exit_action)` 与 `place_order` 的 `action='BUY'` 不一致，line 834）。
- **方案**：开头加 `if not self.connected: return {"status":"skipped"}`；combo 平仓方向与开仓保持一致语义（确认 Tiger SDK 对 combo 平仓是用 leg action 还是 combo action）。

### M5. 期权符号解析未捕获异常
- **位置**：`futu/adapter.py:561` `parse_option_symbol(leg.symbol)` 无 try/except。
- **方案**：包 try/except，坏符号返回 `skipped`/`FAILED` 而非崩溃。

### M6. Geo 回填早于 demo 用户创建
- **位置**：`seed.py:120-121`（session 1 回填）先于 `seed.py:126+`（session 2 创建 demo）。
- **问题**：首次启动（空库 + SEED_DEMO=true）时 demo 用户刚创建，本轮回填已跑完，要等下次重启才补 geo。
- **方案**：把 `_backfill_missing_registration_geo(db)` 调用移到 demo seed 之后（同一 `init_db` 末尾再开一个 session 回填），保证首启即补齐。

### M7. 双 schema 管理路径可能漂移
- **位置**：`seed.py:116-118`（create_all + 手写 ALTER）与 `alembic/versions/001_baseline.py`。
- **方案**：明确分工——生产用 Alembic，开发用 create_all；或在 CI 加 `alembic check` 对比模型与迁移，防止漂移。

### M8. Service Worker 每次取 token 都重新注册
- **位置**：`web/src/lib/firebase.ts:44`（每次 `requestWebFcmToken()` 都 `register`）。
- **方案**：先 `navigator.serviceWorker.getRegistration()`，无则再 register；或注册一次缓存 registration。

## 建议实施顺序

1. **H1 + H2**（FCM 异步化 + 异常兜底）——最高优先，直接影响生产稳定性。
2. **H3 + M5 + M3**（保护单数量/异常/部分保护）——实盘资金安全。
3. **M6**（geo 回填顺序）、**M1**（异步阻塞收敛）——一次性清理。
4. **M2/M4**（保护单价格与方向）——需结合券商回执，单独排期 + 实盘验证。
5. **L 系列**——顺手清理。
